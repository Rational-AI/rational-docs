# Create a workflow

Workflows automate data transformation in Rational AI. This guide covers creating, configuring, and testing the Python steps that convert raw data into AI-ready knowledge.


:::note[What is a workflow?]
Workflows process the files a Knowledge receives: they extract key information, augment it, identify connections between data points, and store the results in the Knowledge for your AI to use. **Settings** → **Workflows** holds two kinds. A **workflow** is a pipeline whose nodes you connect on a graph, and a Knowledge can run it as its **Default workflow**. A **step** is a single Python script, edited and test-run in the browser; workflows call steps as nodes, and the **Classic pipeline** runs the step a [processing rule](/operational-guides/create-processing-rule) picks for each file.
:::

## Prerequisites

Before creating workflows, ensure you have:
- **Create** and **Update** on the **Workflows** row of your role. See [Manage roles and users](/operational-guides/roles-and-users).
- A Knowledge to run them on, to see their results.

### Workflow list
The **Workflows** tab lists everything created in your environment, in four groups:
* **Workflows**: the pipelines a Knowledge can run, each with an enable switch. Select **+** (*"Add workflow"*) to create one.
* **Steps**: the Python scripts, like the one on this page, that a workflow or a [processing rule](/operational-guides/create-processing-rule) calls. Select **+** (*"Add step"*), then **From scratch** or **Import JSON**.
* **Control flow** and **Builtins**: the ready-made nodes a workflow can use. Select one to read its usage and parameters.

The **Processing rules** tab next to **Workflows** holds the [processing rules](/operational-guides/create-processing-rule).

### Workflow editor
A new workflow is created as *Untitled workflow*, switched off. Selecting it opens its code, written with the workflow builder, next to a **Graph** canvas that draws it. On the canvas you can drag nodes to arrange them, drag ports to connect them, and press **Del** to remove them. Select **Save** to keep your changes, or **Undo** to drop them. Switch the workflow on in the list when it is ready.

## Creating your first step
If you're a new user, the page may initially be empty. Create your first step in a few steps:

* Select **+** next to **Steps** (or **Add new** on the empty page), then **From scratch**.
* Replace *Untitled workflow* with a clear and descriptive **name**: for example `PDF processing step`.
* Optionally, add a short **description** explaining its purpose. This is _strongly_ recommended for long-term maintainability.
* Write the code in the editor and select **Save**.

The step's **⋮** menu holds **Workflow Settings** (**Timeout (minutes)**), **Export (JSON)**, **Download** (the `.py` file), **Open in Lab** and **Delete**.

### Capabilities

Under the description, the **Capabilities** field (*"Select capabilities"*) tags a step with the kinds of content it pulls out of a document, such as **Images**, **Tables**, or **Annotations**. The tags don't change what the step does; they describe it, so the platform can surface the right step in the right place.

- **Choose any number.** A step can carry no capabilities, exactly one, or several.
- **Saved with the step.** Your selection is saved when you select **Save**.

:::note[The capability list can grow]
Rational AI loads the list of capabilities from the platform, so new kinds can appear without an update to the interface.
:::

**Capability tags also filter where you pick a step.** When the context requires a capability (for example choosing a workflow from the **Image** tool settings, or running **Auto-annotate images**), the list shows only the steps that carry the matching tag, so you can't select one that can't do the job. Where no specific capability is required, every step is listed.

### Workflow logic

Let's create a simple, yet effective, workflow that takes as input a lorem-ipsum markdown file, creates a Rational Resource associated with it
and performs chunking and embedding automatically, to allow semantic retrieval in a RAG scenario.

The workflow business logic is defined as below:

```python
#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.12"
# dependencies = [
#     "rational-client",
# ]
#
# ///

from rational_client.core import (
    Knowledge,
    File,
)
from rational_client.utils import run


def process(document: File, options: dict):
    # Read document content (bytes)
    content = document.get_data()

    # Convert to string (assumes content is textual)
    text = content.decode("utf-8")
    
    # Get the Knowledge instance this document belongs to
    knowledge = Knowledge(document.knowledge_id)

    # Create a new Rational Resource in the Knowledge Base
    new_resource = knowledge.create_resource(
        name=document.name,
        category="document_category",
        tags=["some", "tags"],
        file_id=document.id,
    )

    # Return the content for chunking and embedding (optional)
    return {str(new_resource.resource_id): text}


run(process)
```

Let's break it down:
- the workflow starts with a header that declares the script dependencies (in the PEP 723 format), so you can use any package, not only an allowlisted set.
- at the bottom we can find the workflow entrypoint, the `run(process)` function, which is an utility function to invoke the `process` function defined
- the workflow business logic is specified in the `process` function: it takes as input the document over which the workflow is applied, and some options that might be used to store values later used in the workflow code
- the workflow typically might invoke operation on Rational AI through the `rational-client` package, such as retrieving a Knowledge handle, that is, `knowledge = Knowledge(document.knowledge_id)`
- the workflow might return a dictionary specifying the Rational Resources created and their textual content, that is, text/markdown, to be automatically chunked and embedded according to the Knowledge settings

### Test a step in the browser

Select **Test run** in the step's editor. Under **Input (JSON)**, provide the step's input: `"file_id"` is loaded as the document, and any other keys are passed as options. Use `{}` for a step that takes no input. Select **Run** to see the **Output**. Save the step before you run it.

### Testing your workflow locally

It is also convenient to perform workflow development on your local machine, before using them into Rational AI.
This is possible and encouraged, as it allows to use your favorite IDE and debugging tools.

Local runs need Python and the [`uv` package manager](https://docs.astral.sh/uv/). To run your workflow locally, make it executable and pass a properly formatted input as argument to it.

Let's suppose to call the above-defined workflow as `lorem-ipsum-wf.py`. We can make it executable by running the command:
```
chmod +x lorem-ipsum-wf.py
```
Then, we need to prepare a Json file as input, let's call it `workflow_input.json`. This file needs to have this structure:
```json
{
    "knowledge_id": "<YOUR KNOWLEDGE ID>",
    "path": "<YOUR DOCUMENT FILEPATH>",
    "options": {}
}
```

Once configured, we can pass the `workflow_input.json` file as input to our workflow, as:
```
./lorem-ipsum-wf.py workflow_input.json
```
to test our workflow locally.

## Make a workflow the default for a Knowledge

A workflow only runs when something asks for it. To have every file of a Knowledge go through it, make it that Knowledge's default.

1. Go to **Settings** → **Knowledge** and open the Knowledge.
2. Select the **Sources** tab.
3. In **Default workflow**, pick your workflow. The list shows the active workflows that belong to this Knowledge and the ones shared at tenant level. **Classic pipeline** routes each file with the **Default processing rule** instead.
4. Select **Save**.

From now on, the workflow runs on every file added to the Knowledge: uploads in the Control Room, files brought in by a source sync, and reprocess requests made through the API without a workflow.

:::note[Force the classic pipeline for one run]
Setting a default doesn't lock you in. When you reprocess a Knowledge from the Control Room you can still choose a different pipeline for that run, and an API client can force the classic pipeline by sending `workflowId` as `null`. Leaving `workflowId` out uses the Knowledge's default.
:::
