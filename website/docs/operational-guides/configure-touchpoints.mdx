# Configure touchpoints

A touchpoint is the bridge between one of your [Knowledges](/operational-guides/create-knowledge) and the people (or systems) asking it questions. It decides two things: who is allowed to reach the agent, and which tools the agent may use when it answers. This guide walks through the touchpoint configuration panel and the **Tools** tab.

:::note[What is a touchpoint?]
A touchpoint connects a Knowledge to the outside world. It carries the access settings for the agent and the set of tools the agent is allowed to use when answering. Those tools come from your installed MCP servers — MCP (Model Context Protocol) is the standard Rational uses to let an AI agent call out to external capabilities like search or database queries. When you create a Knowledge, Rational also creates a default touchpoint for it, which you then refine here.
:::

## Prerequisites

Before you start, make sure you have:

- **Administrative access:** an account with touchpoint management privileges.
- **A touchpoint to configure:** for example the default touchpoint created with your Knowledge.
- **At least one MCP extension installed:** a touchpoint can only offer tools that an installed MCP server exposes (for example the `rational-knowledge-rag` extension). See [Manage extensions](/operational-guides/manage-extensions) if you need to install one.

## Open a touchpoint

Go to **Settings** → **Touchpoints** and select the touchpoint you want to configure. This opens the configuration panel, where access settings live, alongside the **Tools** tab.

:::note[A new touchpoint inherits the platform's model]
Create a touchpoint without naming a model and it takes your platform's default **Conversational model** (the one set under **Settings** → **AI Model Registry** as *"Default model for conversations"*) and adds it to its own list of allowed models. The rule lives in the backend, so it applies equally to touchpoints created through the API. A model you choose explicitly is always kept, and existing touchpoints are left exactly as they are; change the platform default and only touchpoints created afterwards pick it up.
:::

A touchpoint's settings are spread over seven tabs:

| Tab | What you set there |
|-----|--------------------|
| **Settings** | Channel, access, Canvas mode and, on API touchpoints, the [API key](/operational-guides/api-access#give-an-application-its-own-touchpoint-key) |
| **Models** | System prompt, models, and [reasoning, generation limits and response verification](/operational-guides/touchpoint-generation) |
| **Sources** | The knowledge the assistant reads, and whether it [may change it](#let-the-assistant-change-a-knowledge) |
| **Tools** | The MCP tools the assistant may call, when they need confirmation, and how long they may take |
| **Skills** | The [skills](/operational-guides/agent-skills) the assistant can use |
| **Memory** | [Memory and long conversations](/operational-guides/touchpoint-memory) |
| **Test runs** | [Replays of past conversations](/operational-guides/test-touchpoint-changes) against a change |

Changes are saved with **Save** at the bottom of the panel, and **Undo** discards them. Without permission to edit the touchpoint, the form is read-only.

## Edit the system prompt

The **System prompt**, at the top of the **Models** tab, is the standing instruction the agent follows on this touchpoint. Two controls sit beside the field, and both matter once a prompt grows past a few lines:

- **Show unsaved changes** switches the field into a read-only diff view, comparing what's saved against what you've typed. On a long prompt this is the difference between knowing what you changed and hoping you remember. It's disabled while nothing has changed.
- **Expand editor** gives the prompt a much taller editing area, hiding the surrounding fields while you work.

:::note[Test a prompt change before it goes live]
A touchpoint with enough history offers to **replay your change against its real past conversations** when you save, so you can see what came out different before your users do. See [Test a touchpoint change](/operational-guides/test-touchpoint-changes).
:::

### Change the workspace assistant's prompt

The assistant people talk to in the main [Chat](/cr/Chats) is a touchpoint too — the **default touchpoint**, named *Rational AI*. You can rewrite its instructions like any other, for example to give it your company's tone or rules.

1. Go to **Settings** → **Touchpoints** and select **Default touchpoint** at the top of the list. It opens on the **Models** tab.
2. Edit the **System prompt** and save. Changes apply from the next message, in existing chats as well as new ones.
3. To go back to Rational AI's own instructions, select **Restore default**, then **Save**.

:::note[The prompt is yours; permissions and tools are not]
Rewriting the prompt changes how the assistant talks and what it focuses on. Which knowledge each person can reach and which tools are available stay managed by Rational AI: on the default touchpoint every user automatically gets all enabled knowledge they are allowed to read. An empty prompt falls back to the built-in default. The default touchpoint can't be deleted.
:::

## Control who can reach the touchpoint

Use this to decide whether someone must sign in before they can talk to the agent. By default they must.

<img
  src={require('@site/static/img/screens/touchpoint-anonymous.png').default}
  alt="The Allow anonymous access toggle on a touchpoint"
  style={{ width: '100%', maxHeight: '100%', objectFit: 'contain', border: '1px solid #E4E4E7', borderRadius: '6px', boxSizing: 'border-box' }}
/>
*The Allow anonymous access toggle in the touchpoint configuration panel.*

1. In the configuration panel, find the **Allow anonymous access** toggle.
2. Turn it **on** to let anyone reach the touchpoint without authenticating, or leave it **off** to require sign-in.
3. Save the touchpoint to apply the change.

:::note[Off by default]
Only enable **Allow anonymous access** when the touchpoint is genuinely meant to be reached without sign-in, such as a public help assistant. Once saved, the setting persists with the touchpoint.
:::

## Let the assistant change a knowledge

By default an assistant only reads the knowledge attached to it. For an assistant whose job is to keep records up to date (logging a request, updating a customer, filing a document), you can let it write as well, one knowledge at a time.

1. Open the touchpoint's **Sources** tab.
2. On the knowledge you want the assistant to maintain, switch on **Can change records**.
3. Read the confirmation and select **Allow changes**.

The change applies at once, without the touchpoint's **Save**. The assistant can then create and update records, move them between collections and create collections in that knowledge — never delete anything. Each change it makes shows the assistant's name, and people working in the knowledge are told when records have been changed so they can reload. Switch **Can change records** off to take the right back; no confirmation is needed.

:::warning[Anyone who can use the assistant can ask for changes]
The permission belongs to the assistant, not to the person chatting. Everyone who can reach the touchpoint can ask it to change records: people in the chat, applications calling its [API or MCP endpoint](/operational-guides/api-access) and, on a public touchpoint, anonymous visitors. Only someone who can edit the knowledge can switch this on, and it is off by default.
:::

The default touchpoint has no such switch: there, the assistant changes records only within the permissions of the person chatting.

## Work with tools

The **Tools** tab is where you choose exactly which capabilities the agent can call. Open it to see your tools organized in a nested view rather than as a flat table:

- One **card per MCP server**.
- Under each server, a **`CONFIGURATION`** list. A configuration is a named, reusable set of settings (parameters and sources) for that server.
- Each configuration expands to show the tools added under it, listed as **alias · tool name · description**.

A configuration that has no tools yet is marked with an **`Unused`** chip, so you can spot at a glance where nothing has been wired up.

### Reading the two dropdowns

Two pickers drive everything in this tab. Both render as grouped, styled lists so you can see where each option comes from.

- **Add tool…** shows a **group header per MCP server** (with the extension's icon) and the tool rows indented beneath it. For example, the `rational-knowledge-rag` extension appears under a **RAG MCP server** group with its tools listed below: `rag_query_simple`, `get_resource`, `get_user_context`, `get_schema`, `execute_query`, `list_databases`, and `rag_query_graph`.
- **Add MCP server configuration…** offers **+ Add new configuration** at the top and then lists the available configurations, each shown with the server icon and an expand chevron.

## Decide when a tool needs confirmation

Choosing which tools an agent *may* call is one decision; choosing which of those calls a human has to approve first is another. The second one sits at the top of the same **Tools** tab, under **When to ask for confirmation** — *"Before running a tool, the assistant can ask the user to confirm."*

1. In the **Tools** tab, open the **When to ask for confirmation** dropdown.
2. Choose the policy for this touchpoint:
   - **Never — tools run without asking.**
   - **Smart — only for sensitive tools (recommended).** The default: read-only tools run straight through, sensitive ones wait.
   - **Always — ask before every tool.**
3. Save the touchpoint.

Under **Smart**, what counts as sensitive is set per tool. Each tool row carries a **Sensitive** badge you can select to add or remove, whatever the current policy is. Hovering it tells you where the current answer comes from — your own override (*"You marked this tool as sensitive."*) or the MCP server's declaration (*"Declared as sensitive by the MCP server."*, *"Not declared as sensitive by the MCP server."*).

When a gated call comes up, the chat pauses and shows an approval card above the composer; the tool runs only once the user approves it.

:::note[The server's annotation is only a default]
An MCP server declares its own tools read-only or destructive, and Rational AI follows that declaration until you say otherwise. Once you have toggled a tool's **Sensitive** badge, your choice is what counts — including across extension re-syncs, which would otherwise reset the tool to whatever the server currently claims.
:::

## Set how long a tool may take

An MCP tool that never answers would otherwise leave the conversation waiting. Every tool call has a time limit: when it runs out, the call is reported to the assistant as failed and the conversation carries on.

1. In the **Tools** tab, find **How long a tool may take**, above the MCP servers.
2. Enter a limit in **seconds**, or leave it empty for the default of 120 seconds. The maximum is 600.
3. Save the touchpoint.

The limit applies to every MCP server on the touchpoint. To give one slow server more time (or less), set **Tool call time limit** in that server's configuration dialog; leave it empty to follow the touchpoint's limit.

:::note[A tool that keeps timing out stops the answer]
One slow call is only a failed step. If the tool runs out of time on every attempt, the answer stops with *"Generation stopped: the tool "…" ran out of time on every attempt."* and a **Regenerate response** button. That's the moment to raise the limit for that server, or to look at why it is slow.
:::

## Add a single tool

Reach for this when you want one specific capability with parameters tuned exactly how you like.

1. In the **Tools** tab, open the **Add tool…** dropdown and select a tool from its MCP server group.
2. In the **Add tool** dialog, set each parameter's mode using its **Default / Auto / Manual** dropdown. **Default** inherits the configuration's value, **Auto** lets the agent decide at answer time, and **Manual** lets you fix the value yourself.
3. To undo a change to any parameter, use the **revert-to-default** button next to its mode dropdown. The button disables itself once the parameter is back in default mode.
4. Select **Confirm**.

### Fill a Manual parameter from the conversation

A **Manual** parameter doesn't have to be a fixed literal. It can reference a value carried on the conversation, resolved at the moment the tool is called:

- `${userStore.<key>}` — a value from the conversation's **user store**.
- `${system.<key>}` — a value from its **system store**, which is set when the conversation is created.

The practical difference between the two is *when* you can write them. The system store is fixed at creation, so an integration that embeds a chat surface it doesn't control the bootstrap of can't use it; the user store can be written afterwards, so it works in that case too.

:::warning[This is how you pass a value the model must not choose]
A parameter set to **Manual** is stripped from the tool schema the model is shown. The model never sees it, so it cannot set it, alter it, or be talked into changing it — the value is substituted after the model has decided to make the call.

That makes it the right mechanism for the caller's identity, a tenant reference, or a capability issued by the host: anything where letting the model supply the value would be the vulnerability.

The alternative (having the agent read a value with a tool like `get_user_context` and pass it back as an argument) routes exactly that value through the model, which is the exposure Manual parameters exist to avoid. If a value matters for authorization, it belongs in a Manual parameter, not in the conversation.
:::

:::note[Single-configuration shortcut]
When the server has only one configuration, the configuration dropdown is hidden in the **Add tool** dialog — there is nothing to choose between.
:::

## Bulk-add a configuration's tools

When you trust a configuration's defaults and want everything it offers, add all of its tools in one action instead of picking them one by one. There are two entry points:

- **Pick a configuration** in the **Add MCP server configuration…** picker to add all of its tools at once.
- Use the **Add all tools** action on a configuration row, found in its `⋮` menu.

Each tool is created with no parameter overrides, so it inherits the configuration and tool defaults. Any required field that has no default falls back to LLM **Auto** — exactly as if you had added the tool individually and left its defaults untouched.

When the bulk-add finishes, a toast confirms the result, for example **Added 2 tools**.

:::note[What gets skipped]
Tools already present are skipped (deduplicated by tool id). If a configuration is empty or already fully added, nothing is created and you get an info toast instead. Partial failures report counts without losing the tools that succeeded.
:::

## Add a new MCP server configuration

Create a configuration when you want a named, reusable set of settings for a server — for example one configuration pointed at a specific data source, ready to drop tools into.

1. In the configuration picker, select **+ Add new configuration**.
2. In the **New MCP server configuration** dialog, choose the **server** from the dropdown.
3. Enter the **configuration name** in the top-level name field.
4. Fill in the collapsible **Params** and **Sources** sections. Sources resolve from the selected server, so they are available while you create a configuration, not only when editing one later.

## Point a tool at a specific Knowledge

Some tools take a knowledge-reference parameter (`knowledgeId` / `knowledge_id`) to say which Knowledge they should act against. Rather than asking you to paste a raw ID, this parameter renders as a **searchable knowledge dropdown**.

1. In the **Add tool** dialog, find the knowledge-id parameter.
2. Set its mode to **Manual** to override it, or leave it on **Auto** / **Default** to let the agent resolve it.
3. Open the dropdown and **filter by name** to find the Knowledge you want. The touchpoint's knowledges are shown by **name** and resolved to their **id** behind the scenes.

:::note[No more raw IDs]
Because knowledge IDs are never surfaced in the UI, this dropdown is the supported way to pick a Knowledge for a manual override — there is no need to type an ID by hand. The same auto/manual/default modes and validation as the other tool-parameter controls apply.
:::

## Result

Your touchpoint now controls its own access through the **Allow anonymous access** toggle, starts from the platform's default conversational model unless you pick one yourself, may keep the knowledge you choose up to date, bounds how long each tool call may take, presents a nested **Tools** view grouped by MCP server and configuration, decides through **When to ask for confirmation** which calls need a human to approve them, and lets you add tools either one at a time or in bulk with defaults inherited. Knowledge-id parameters are filled from a searchable dropdown instead of raw IDs — so the agent has exactly the tools and references it needs to answer against your Knowledge.
