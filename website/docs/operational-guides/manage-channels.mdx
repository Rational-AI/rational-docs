# Manage channels

A channel connects a Telegram bot, a mailbox, or a Microsoft Teams or Slack bot to Rational AI, so a [touchpoint](/operational-guides/configure-touchpoints) can answer the people who write there. An Email channel can also start an agent of [Agents](/cr/Agents) when a new email arrives.

*The **Channels** list: each channel, its type, who provides it, and its mode.*

Messages that come in become conversations you can read in [Conversations](/cr/Conversations), and replies go back out over the same channel.

## Prerequisites

- **Permissions:** a role with **Create** and **Update** on **Channels** (see [Roles and users](/operational-guides/roles-and-users)).
- **The credentials for the surface you're connecting.** For example a Telegram bot token, a mailbox login, or the app credentials of a Microsoft Teams or Slack bot. See the per-type guides below.

## Choose a channel type

Two kinds of channel exist, and they behave differently once connected.

**Native channels** are built into the platform, with their own connection handling, status reporting and message support:

| Type | Setup |
|------|-------|
| **Telegram** | [Connect a Telegram bot](/operational-guides/connect-telegram) |
| **Email** | [Connect a mailbox](/operational-guides/connect-email) |
| **Microsoft Teams** | [Connect a Microsoft Teams bot](/operational-guides/connect-teams) |
| **Slack** | [Connect a Slack app](/operational-guides/connect-slack) |

**Extension-provided channels** come from an [extension](/operational-guides/manage-extensions) that declares a channel provider, for example **WhatsApp (OpenWA)**, which connects a WhatsApp number through a self-hosted OpenWA server. They're driven by the extension rather than by the platform, so what they support depends on the extension.

The web chat and the OpenAI-compatible API are built-in channels of the platform. They aren't in the type list, so you can't create another one.

## Create a channel

1. Go to **Settings** → **Channels** and select **Add**.
2. Choose the **Channel type**. The list has the native types and the channel providers of your installed extensions.
3. Enter a **Name**. It must be unique across all channels, and names are case-sensitive.
4. Fill in the **Configuration** fields the type asks for.
5. Set the **Reply mode** (see [Choose the mode](#choose-the-mode)).
6. Optionally, enter a **Description**.
7. Select **Save**.
8. Open the touchpoint that should answer and, on its **Settings** tab, select this channel as its **Channel**. See [Configure touchpoints](/operational-guides/configure-touchpoints).

:::note[The provider is fixed at creation]
A channel's type and provider are chosen when you create it and can't be changed afterwards. Everything else (the name, the mode, the credentials, the policies) stays editable. If you need a different provider, create a new channel.
:::

## Choose the mode

The **Reply mode** decides whether the assistant answers by itself or a person does.

| Mode | What happens to an incoming message |
|------|-------------------------------------|
| **Automatic** | The assistant replies on its own. |
| **Manual** | The conversation is assigned to an operator. Nothing is sent until a person replies. |

Use **Manual** when you want conversations captured and visible but answered by people, for example on a mailbox you're still evaluating.

## Connect, check, and disconnect

Native channels show their connection state under **Connection** in the channel's details drawer, along with **Connect**, **Reconnect**, **Disconnect** and **Edit configuration**.

- **Connect** checks your credentials with the service. A wrong bot token or a rejected mailbox login fails here.
- **Status** reports what the connection is doing: connected, in error, or disconnected. Email adds a state for a mailbox still waiting for **Authorize mailbox access**, and one for a mailbox that no touchpoint uses and no agent is bound to.
- **Disconnect** stops the channel and clears its connection state, but keeps its configuration so you can connect it again. An Email channel also drops its OAuth tokens.

Editing a Telegram channel checks the bot token again and brings the bot in line with the new settings, so the old configuration doesn't stay live. **Reconnect** runs the connection check again for any type.

Bot tokens, mailbox passwords and OAuth secrets are shown masked. You can edit other fields and save without retyping them; enter a credential only to replace it.

## Control who can write in

Once a native channel is connected, its details drawer has a **Reply filter**, saved with **Save reply filter**. The same lists appear in the channel's form as **Allowed senders** and **Blocked senders**.

- **Allowed senders**: leave it empty and anyone who can reach the surface can start a conversation; fill it in and everyone else is ignored.
- **Blocked senders**: always ignored, even when the allow-list would admit them.

Messages from senders that aren't allowed are dropped without a reply. An Email channel also shows how many emails it ignored, and from whom.

Telegram, Slack and Email also ignore other bots and automated mail, so two systems can't get into a reply loop with each other. The per-type guides describe exactly what each one screens out.

## Control what can be sent in

Telegram and Email channels have attachment settings, and so do extension-provided channels whose provider declares them. Microsoft Teams and Slack channels pass on text only.

- **Accept attachments**: whether files, photos and voice notes sent to this channel are accepted at all.
- **Attachment types**: a comma-separated list of file extensions or MIME prefixes (for example `pdf, docx, image/`). Leave it empty to accept every type; anything not listed is rejected.
- **Attachment size limit (MB)**: the largest file accepted. The ceiling is 25 MB. Telegram's default is 20 MB, the most a Telegram bot can download.

The assistant reads accepted files as it does files attached in the chat: it sees photos when the model supports images, reads the text of documents, and reads a voice note's transcript as what the user said. If a voice note can't be transcribed, the assistant is told so. Operators can open or download what arrived; see [Use the chat](/operational-guides/chat-experience).

## Shape how the assistant replies

People on messaging apps write several short messages in a row and expect short messages back. Two settings adapt the assistant to that, on channels whose form offers them.

### Split replies into several short messages

On Microsoft Teams, Slack, and some extension-provided channels, turn on **Split replies** to deliver each reply as a few short messages instead of one long block.

The reply is cut at blank lines into at most four messages, sent a second or so apart. Code blocks and lists are never cut. [Conversations](/cr/Conversations) still shows the reply as one message.

### Wait until the sender pauses

Without a delay, every incoming message starts its own answer, so a user who sends *"hi"*, then a question, then a voice note gets three replies talking over each other. Channels that offer **Reply delay (seconds)** can hold the reply instead. Only some [extension-provided channels](#choose-a-channel-type) offer it.

| Setting | What it does |
|---|---|
| **Reply delay (seconds)** | How long the assistant waits after a message before replying. Each new message restarts the wait. `0` replies to each message at once. |
| **Longest reply wait (seconds)** | The longest the assistant holds its reply, counted from the first unanswered message, so a user who keeps writing still gets an answer. Defaults to 90. |

When the wait ends, the assistant answers once, with the whole burst of messages in context. The delay applies only in **Automatic** mode, and only to conversations that come in through a channel; the web chat always answers at once.
