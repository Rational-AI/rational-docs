# Back up and restore an on-premises installation

An on-premises Rational AI installation keeps its data in several places: a PostgreSQL database, a vector store, an object storage, the installed extensions and the knowledge databases. **Settings** → **Backup** copies all of them, in one run, to a destination you own (a network share, an S3 bucket, an FTP or SFTP server, or a mounted folder) on a daily schedule or on demand. This guide covers what a backup contains, how to set the destination up, how to check that backups are really happening, and how to bring an installation back from one with the `rational` command on the host.

:::note[On-premises only]
The Backup page is on by default on every on-premises installation set up with `install.sh` (see [Install and update](./install-and-update)): it only needs a destination. On the managed cloud the platform backs the data up for you and the page is not shown.
:::

:::note[The backups taken before every update are not enough]
Every update takes a local backup first, so a bad release can be rolled back. Those backups stay on the same disk as the installation: a failed disk or a lost machine takes them along. The backup on this page goes to a destination of yours, away from the machine. Set it up on every installation that holds data you care about.

| | Local backup (`rational backup`) | Off-site backup (**Settings** → **Backup**) |
|---|---|---|
| Protects against | A bad update | A lost machine or disk, a deleted knowledge base |
| When | Before every update, or by hand | Daily, or **Back up now** |
| Where | `/opt/rational/backups/` on the same disk | Your NAS, S3 bucket or FTP/SFTP server |
| Restore with | `rational restore DIR` or `rational rollback` | `rational offsite-restore NAME` |
:::

## What a backup contains

| Component | What is captured | How |
|-----------|------------------|-----|
| **postgres** | Every database on the server: the application data of every tenant, the workflow engine, the identity provider. This is also where the key ring that protects stored credentials lives, so a backup is sensitive material. Keep the destination as private as the installation itself. | One `pg_dump` per database plus the roles, streamed to the destination |
| **qdrant** | The vector collections (embeddings behind knowledge retrieval) | One snapshot per collection, streamed to the destination and removed from the vector store afterwards |
| **storage** | The object storage: attachments, synced source files, extension packages | An incremental mirror in the `storage/` folder of the destination, shared by every backup |
| **extensions** | The installed extensions directory | A `tar.gz` per backup |
| **sqld** | The knowledge databases (Rational BI, SQLite resources) | A `tar.gz` per backup |

Each run produces a folder named after its UTC start time (`2026-09-09T02-30-00Z`) with a `manifest.json` describing what it holds. The object-storage mirror is **never pruned**: files deleted from the application stay in the mirror, so every dump, old or new, finds the attachments it references. Retention only removes whole backup folders.

:::note[What is not backed up]
The weights of the models the installation runs, the audio model cache and the Python package caches are not part of a backup: they are re-downloaded on demand after a restore. The session cache is not backed up either; after a restore everyone signs in again.
:::

## Prerequisites

Before you start, make sure you have:

- **Administrative access.** The page is admin-gated.
- **Backup enabled on the installation.** Installations set up with `install.sh` have it on. A stack you assembled yourself with Docker Compose needs `Backup__Enabled=true` on the backend, and the worker that performs the backup (`temporal-worker`) needs to know where the live data is:

  | Variable | Value on a Compose installation |
  |----------|--------------------------------|
  | `BACKUP_POSTGRES_URL` | `postgresql://postgres:<password>@db:5432/postgres` |
  | `BACKUP_QDRANT_URL` | `http://vectordb:6333` (plus `BACKUP_QDRANT_API_KEY` if one is set) |
  | `BACKUP_EXTENSIONS_PATH` | The extensions directory, mounted into the worker (for example `./data/extensions:/rationalai/backend/extensions`) |
  | `BACKUP_SQLD_PATH` | The libsql data directory, mounted into the worker (for example `./data/sqld:/backup/sqld`) |

  A component whose variable is missing is reported as *skipped*, not as a failure.
- **A destination with enough space** for the database dumps, the vector snapshots and a full copy of the object storage. The worker itself needs no free disk: everything is streamed.

## Set the destination

Go to **Settings** → **Backup** and pick the destination **Type**. The fields change with the type:

| Type | Fields | Path |
|------|--------|------|
| **Network share (SMB / Samba)** | Host, port (445), user, password, domain | Share and folder, for example, `backups/rational` |
| **S3 bucket** | Endpoint, provider (`Other` for a NAS or MinIO, `AWS` for Amazon), region, access key ID, secret access key | Bucket and prefix, for example, `my-bucket/rational` |
| **FTP server** | Host, port (21), user, password | Folder |
| **SFTP server** | Host, port (22), user, password | Folder |
| **Local folder (NFS mount)** | None | The absolute path of a folder the worker can see, typically an NFS mount added to the worker container |

On an installation set up with `install.sh`, do not choose **Local folder**: the path is inside the worker's container, is lost with it, and cannot be restored with `rational offsite-restore`. Ask the owner of the destination for an account that can write only the backup folder.

The folder is created on first use. Click **Test destination** before saving: the worker writes and deletes a small marker file there, which proves the credentials, the path and the write permission in one go. A failure comes back with the reason (a wrong password, a read-only share, an unreachable host).

:::warning[Prefer SFTP or S3 over FTP]
Plain FTP sends the password and the data in clear and cannot verify what it wrote. It is supported for legacy targets; when the same server offers SFTP, use that.
:::

Passwords and access keys are stored encrypted. When you come back to the page they show as `********`; leave them as they are to keep the stored value, or type a new one to replace it.

## Schedule

**Daily backup** runs a backup every day at the **Time of day** shown, in the time zone of your browser at the moment you save. A run that is still going when the next one is due is not interrupted; the next one is skipped.

Pick a quiet hour, away from 03:00, when the installation updates itself. The knowledge databases are copied file by file while the application runs, so a knowledge base written during the backup can come back inconsistent.

## Retention

After each successful run the destination is pruned. Choose in **Keep** how much history to hold:

| Option | Keeps |
|--------|-------|
| **Last 7 backups** | The newest seven, whatever their age |
| **One month, a backup per day** | The newest seven, and one per day for 31 days |
| **Three months: daily for a week, then weekly** | The newest seven, and one per week for 13 weeks |
| **One year: daily for a week, weekly for two months, then monthly** | The newest seven, one per week for 9 weeks, and one per month for 12 months |
| **Everything, never delete** | Every backup |

A policy set through the API (`PUT /management/v0/backup`) that matches none of these is shown as **Custom** and kept as it is. Only the dumps and snapshots are pruned; the object-storage mirror is shared by every backup and is never removed.

Click **Save**. The **Next scheduled backup** line under *Last backup* confirms the schedule is registered.

## Back up now, and check it happened

**Back up now** starts a backup immediately. While it runs the page shows each component as it is captured; when it finishes, *Last backup* shows the time, the outcome, the size and the folder name, and the backup appears under **Backups at the destination**.

A failed run reports the error in place of the size. A backup that fails half-way is removed from the destination, so whatever is listed there is complete and restorable.

Two things are worth checking now and then:

- **Last backup** keeps moving and says *completed*. A schedule nobody watches is a schedule that can silently stop.
- The list under **Backups at the destination** is what the destination actually holds, read from it each time the page loads, not a log kept by the application. If the destination disappears, so does the list.

## Restore

Restoring replaces the current data with a backup, which is why it is not a button: the application must be stopped while its databases are dropped and recreated. It runs from a shell on the machine, with the `rational` command.

:::danger[A restore overwrites everything]
Every database, the vectors, the object storage, the extensions and the knowledge databases are replaced by the backup's contents. Anything created after that backup was taken is lost. Take a fresh backup first if there is any doubt.
:::

### Give the machine its copy of the destination

The application keeps the destination's password encrypted, so the machine needs its own copy of the destination settings in `/opt/rational/backup-destination.env`. Do this once, when you set the destination up, not on the day you need it.

1. In **Backups at the destination**, click **Copy restore command** on any backup. It copies the destination settings as variables; the secrets are masked as `********`.
2. On the machine, create the file, readable by root only, and paste the variables into it:

   ```bash
   sudo install -m 0600 /dev/null /opt/rational/backup-destination.env
   sudo nano /opt/rational/backup-destination.env
   ```

   Keep only the `NAME=value` lines; a leading `-e ` and a trailing `\` are tolerated. Write the real password in place of `********`. It looks like this:

   ```bash
   RCLONE_CONFIG_BACKUP_TYPE=sftp
   RCLONE_CONFIG_BACKUP_HOST='nas.example.lan'
   RCLONE_CONFIG_BACKUP_USER='rational'
   RCLONE_CONFIG_BACKUP_PASS='<the password>'
   BACKUP_ROOT='backup:rational'
   ```

3. Check that the machine can read the destination:

   ```bash
   sudo rational offsite-list
   ```

   It lists each backup with its size and what it holds.
4. Keep a copy of this file and of `/opt/rational/.env` **off the machine**, separately from the backups. Neither is part of a backup, and a replacement machine cannot read the backups without them.

### Restore a backup

1. Choose the backup with `sudo rational offsite-list`.
2. Run the restore with its name:

   ```bash
   sudo rational offsite-restore 2026-09-30T01-30-00Z
   ```

   It checks the backup while the application is still running, then asks you to type the backup name again to confirm. It stops the application, restores the databases, the vectors, the files, the extensions and the knowledge databases, and starts everything again.

   | Option | When to use it |
   |--------|----------------|
   | `--only postgres,qdrant,storage,extensions,sqld` | Restore only some components, for example `--only qdrant,sqld`. |
   | `--yes` | Skip the confirmation, for a script. |

3. Sign in and check a recent conversation, a knowledge base and an extension. Extensions may take a moment on first use while their packages are downloaded again.

A restore that fails part-way leaves the application stopped: run it again, or go back to a local backup with `sudo rational restore /opt/rational/backups/<folder>`.

:::note[The command on the page is for stacks you assembled yourself]
**Copy restore command** gives a `docker compose run … temporal-worker rational-backup restore` command. On an installation set up with `install.sh`, use it only as the source of the destination settings and restore with `rational offsite-restore`, which stops the right services and mounts the right folders.
:::

A few consequences to know about:

- Everyone is signed out: sessions are not part of a backup.
- The backup includes the workflow engine's state. A backup run that was in progress when that backup was taken may resume and complete after the restore; it is harmless.
- Restore into the **same release** of Rational AI that took the backup, or a newer one: the application migrates the database forward on start, never backwards.

### Restore on a replacement machine

1. Put the saved `.env` at `/opt/rational/.env` on the new machine **before** installing: the installation keeps the secrets it finds there, and the restored data refers to some of them.
2. Install with `install.sh` (see [Install and update](./install-and-update)).
3. Write `/opt/rational/backup-destination.env` from your saved copy and run `sudo rational offsite-restore NAME`.
4. If **Settings** → **Licence** asks for it, activate the license again.

### Rehearse it

A backup that has never been restored is a hope, not a plan. Restore into a spare installation once after setting the destination up, and again after major updates: it is the only way to know the destination is really usable.

## Limits

- **Backups are not encrypted.** The dumps and archives are stored as they are; the destination's own access control and disk encryption are the protection.
- **Not in the backup:** `/opt/rational/.env` (the secrets), the certificates, the connection to Rational AI and `backup-destination.env`. Keep `.env` and `backup-destination.env` off the machine, separately from the backups.
- **The object-storage mirror only grows:** deleted attachments stay there.

## Troubleshooting

| Symptom | Likely cause |
|---------|--------------|
| **Test destination** fails with *permission denied* | The share or folder is read-only for the given user. |
| The status shows *failed* with *pg_dump: server version mismatch* | The worker image is older than the database server; update the worker. |
| A component is *skipped* | Its `BACKUP_*` variable is not set on the worker, or the path it points at does not exist there. |
| The backups list is empty though runs completed | The destination path was changed after those runs: the list reads the current path. |
| `rational offsite-restore` says *no off-site destination* | `/opt/rational/backup-destination.env` is missing: see [Give the machine its copy of the destination](#give-the-machine-its-copy-of-the-destination). |
| `rational offsite-restore` says a value is still the `********` mask | Write the real password in `backup-destination.env`. |
| `rational offsite-restore` says *a local destination is not kept on this host* | The destination is a **Local folder**. Switch to SMB, SFTP, FTP or S3. |
