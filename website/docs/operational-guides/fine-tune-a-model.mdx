# Fine-tune a model with your own data

Fine-tuning takes a general-purpose AI model and trains it further on your own examples, so it gets noticeably better at the specific tasks you care about. This guide walks you through the whole process end to end: assembling your training data as a dataset, then launching a fine-tuning run and using the result.

:::note[What is fine-tuning?]
A *base model* is a general, pretrained AI model (see [LLMs](/concepts/LLMs)) that already knows a lot but nothing about your particular use case. *Fine-tuning* nudges that base model toward your data by showing it more examples. Those examples live in a *dataset*: a collection of inputs and the outputs you'd like the model to produce. In Rational AI this is a two-part job: you build a dataset under **Datasets**, then train on it under **Fine-Tuning**.
:::

## Prerequisites

Before you start, make sure you have:

- **Administrative access:** an account with permission to reach the **Settings** area.
- **A base model available:** at least one model you can train from, visible in the [AI Model Registry](/operational-guides/ai-model-registry-features).
- **Training examples ready:** either a dataset file to upload, or recorded traffic and events you can build a dataset from.

## Create a dataset

A dataset is the training data your fine-tuning run will learn from. You manage datasets under **Settings** → **Datasets**, where the table lists each one by **Name**, **Format**, **Entries**, **Created at**, **Updated at**, and **Current version**.

Datasets are versioned: you can edit the data and create new versions later, so you're never locked into your first attempt.

To start, select **New**. The menu offers several ways to build a dataset.

### From a file

Choose **From file** when you already have your examples prepared as a dataset file. Upload the file, and Rational AI reads its entries into a new dataset. This is the most direct path if your data was exported from another tool or assembled by hand.

### From recorded traffic

This is the option to reach for when you want to fine-tune the thing this product actually runs: an **agent**.

Every chat completion that goes through the proxy is recorded as the conversation the model actually saw, **including the system prompt, the tool calls it made, and what those tools returned**. Building a dataset from that captures the agent's real behavior rather than an approximation of it.

Filter down to the examples you want with the fields you can actually answer:

- **Touchpoint**: which agent's traffic.
- **Model**: which model produced it.
- **Date range.**
- **Successful calls only**: exclude the ones that errored.

The counts update as you type: how many requests match, how many will become training examples, and how many are held out. You can see the size of what you're about to create before you create it.

:::note[A dataset doesn't evaporate when your retention policy fires]
Entries **copy** the content they were built from rather than pointing at it. Captured request bodies have their own retention clock, and a dataset whose examples vanished on the next sweep would not be a dataset.

So building a dataset from recorded traffic is also a way of preserving those specific examples past your retention window. That's worth knowing in both directions.
:::

### From events

**From events** builds a dataset out of room events (the text of each turn). It works without any proxy traffic, so it's the option for a tenant that doesn't have any.

Its limitation is worth knowing before you choose it: **an event carries the text of a turn and nothing else**. There's no system prompt, no tool call, no tool result. If you're fine-tuning an agent that uses tools, this source cannot express the behavior you're trying to teach. Use recorded traffic where you have it.

## Curate a dataset

A dataset built from real traffic will contain examples you don't want to train on. Open one and its entries are rendered as the conversations they are (tool calls shown as `name(arguments)` rather than raw JSON), each carrying a chip showing whether it's a **training** or **held-out** example.

- **Removing** an example is a single action from the example itself. Most curation is removal, so it's the quick one.
- **Correcting** one opens it as JSON. The shape differs by format, and a form modeling only some formats would silently drop whatever it didn't recognize.
- A format that genuinely can't be edited **says so**, rather than accepting an edit and quietly discarding it.

:::note[The held-out split, and why it matters]
Every dataset is split into **training** examples and **held-out** ones. The held-out set is never trained on. It's what the run is scored against, so the score reflects performance on examples the model has genuinely never seen.

The split is assigned when the dataset is created, so it's reproducible, and it's **interleaved** rather than taken as a block from one end, because holding out only your oldest or newest traffic would evaluate against a skewed sample.
:::

:::warning[Runs from before this shipped reported a meaningless score]
Earlier releases recorded which split an entry belonged to and then trained on the whole dataset anyway. A model scored on examples it was trained on reports a number that tells you nothing, which is the exact failure a split exists to prevent.

The two halves are now fetched separately and the held-out set is handed to the trainer as its evaluation set. If you're comparing a new run against one from before this change, **the old evaluation numbers aren't a valid baseline.** Re-run it if the comparison matters.
:::

## Start a fine-tuning run

With a dataset in place, go to **Settings** → **Fine-Tuning**. The table here lists your runs by **Name**, **Base model**, **Training dataset**, and **Created at**.

Select **New** to open the **New fine-tuning** dialog, then fill it in:

1. Enter a clear **Name** and a short **Description** so your team can tell runs apart later.
2. Pick a **Base model** (the existing model you want to train further).
3. Select a **Dataset**, the training data the model will learn from.
4. Review the training and adapter parameters (explained below), then select **Launch**.
5. Confirm with **Start training**. You'll see *"Fine-tuning launched"* and the run appears in the list.

If the training job can't be started, the run is still saved and Rational AI tells you to check its status before retrying, so you don't end up with two copies of the same run.

*Starting a fine-tuning run: pick a **Base model** and a **Dataset**, set the training parameters, then **Launch**.*

### Training parameters

These settings control how the training runs:

- **Learning Rate:** how big an adjustment the model makes at each step, picked from a list of values from `1e-5` to `5e-4`. The default is `2e-4`. Too big and it overshoots; too small and it barely learns.
- **Batch Size:** how many examples the model looks at before each adjustment. The default is 1.
- **Epochs:** how many full passes the run makes over the whole dataset. The default is 1. A run is bounded by epochs rather than by a fixed number of steps, so doubling your dataset gives you the same number of passes over it rather than half.

### Adapter settings

Fine-tuning here trains a small **adapter** (a LoRA adapter) on top of the base model rather than rewriting the whole thing. Three settings, in the collapsible **LoRA parameters** section, control the adapter's capacity, and they're the ones to reach for when a run is **underfitting** (learning too little from your data):

- **Rank:** how much capacity the adapter has, 16 by default. The main dial. Raise it when a run isn't learning enough from your examples or the task is more varied.
- **Alpha:** how strongly the adapter's contribution is scaled, 16 by default. It is usually equal to the rank, so while the two are equal, changing **Rank** changes **Alpha** with it.
- **Dropout:** how much regularisation is applied during training, between 0 and 0.99, 0 by default. Raise it if the model starts memorising your examples instead of learning from them.

:::note[Leave the defaults alone to start]
Every parameter ships with a sensible default, and launching without touching any of them gives you a reasonable run. Change one when you have a specific reason and a first result to compare against.

If you do need to intervene, the rule of thumb is that the training parameters shape *how* the run proceeds, while the **adapter settings** are what change how much it can learn at all. A run that plateaus early is usually a rank problem, not a learning-rate one.
:::

:::note[Template and quantization are handled for you]
Two things you don't set, and shouldn't have to:

**The conversation template follows your base model.** Training a Llama or Mistral base uses that family's own markers rather than another family's. A mismatch here trains the model on tokens it never sees at inference and fails silently, producing a run that completes and a model that doesn't work. An unrecognized family keeps its own tokenizer's template rather than borrowing one.

**Quantization follows the model size.** It stays off where full precision fits, since quantising costs quality, and switches on above that, where the alternative isn't a slower run but no run at all, because the weights don't fit on the cards.
:::

## Watch a run

Training takes a while, and a job that reports nothing but "running" is impossible to make decisions about. Select a run in the list to open its drawer, which shows what it's actually doing and refreshes every few seconds while the run is live:

- **Status**: **Pending**, **Training**, **Completed**, **Failed** or **Canceled**, along with who created the run and its **Duration**.
- **Progress**: a bar with the percentage, the current step and the latest loss.
- **Learning curves**: a chart of **Training loss** and **Evaluation loss** step by step. Because the run is evaluated against the held-out split, you can see **overfitting while it's still happening**. Training loss falling while evaluation loss flattens or rises is the signal to stop.
- **Error**: the failure reason, if it fails, rather than a run that stops.
- **Parameters**: the batch size, epochs, learning rate and LoRA settings the run actually used.

The chart shows the latest 2,000 measurements; the complete history is in the run's training artifacts (see below). If the measurements can't be loaded, the drawer says so and offers **Reload measurements** to try again.

The drawer's **⋮** menu holds what you can do with the run:

| Action | When it's offered | What it does |
|---|---|---|
| **Cancel run** | While training | Stops the training job and releases its GPUs. Saved checkpoints are kept. |
| **Retry run** | Failed or canceled | Starts the same run again, from its latest complete checkpoint when there is one. |
| **Start training** | Pending | Captures the dataset as it is now and starts training. |
| **Re-run** | Always | Opens the dialog pre-filled with this run's settings, to launch a *new* run with different parameters. |
| **Edit details** | Always | Changes the name and description only. |
| **Download training artifacts** | Completed or failed | Downloads everything needed to audit or reproduce the run. |
| **Delete** | Not while training | Removes the run. |

Canceling is also what frees the GPUs, so cancel a run you've already learned from rather than letting it finish out of politeness.

### Resume a run instead of starting over

A long run that fails at 80% shouldn't cost you the first 80%. While it trains, a run saves a checkpoint every 100 steps, and the first time it starts it captures its training inputs: the dataset entries, the model and the configuration.

**Retry run** picks up from the latest complete checkpoint, using those same captured inputs. If no checkpoint was saved yet, training starts again from the beginning. The same happens on its own when a training job is restarted after an infrastructure failure.

:::note[A retry trains on what the run started with]
Because the inputs are captured when a run first starts, editing the dataset afterwards doesn't change what a retry trains on. That's what makes resuming safe. When you *want* different data, a different base model or new parameters, use **Re-run** to create a new run. Checkpoints that were only partly written are skipped rather than resumed from.
:::

:::note[A backend restart no longer strands a run]
Run status is reconciled by reading the job back from the cluster, so a restart mid-training doesn't leave a run showing "training" forever with weights that never register. If you have runs stuck in that state from an earlier release, they're the symptom of that old behavior rather than something still happening.
:::

## Use your fine-tuned model

When the run finishes, **Deploy** in its drawer makes the fine-tuned model available in the [AI Model Registry](/operational-guides/ai-model-registry-features) alongside your other models. It's the same thing the registry's **Install your own fine-tuned model** option points to. From there you can activate it and use it like any other model in Rational AI. Deploying never silently replaces a deployment that is already serving.

### Take the weights with you

To run the model somewhere else, or keep a copy outside the platform, open the run's **⋮** menu in the list and select **Download weights**. It is enabled once the run is **Completed**, and downloads `<run name>-weights.tar.gz`: the trained LoRA adapter, its configuration and the tokenizer, ready to load on top of the same base model.

**Download training artifacts**, in the drawer, is the bigger package: `<run name>-training.tar.gz` with the captured inputs, the resumable checkpoints, the configuration and the full measurement history. It needs read access to both the run and its dataset, since it contains the training data.

## Result

You've assembled a dataset (ideally from recorded traffic, so tool calls and system prompts survive into training), curated out the examples you didn't want, and launched a run whose parameters are actually applied. You can watch its learning curves against a genuinely held-out split, stop it when it stops improving, resume it from its last checkpoint if it fails, deploy the result into the model registry, and download its weights to use elsewhere. To keep improving it, curate the dataset and launch another run.
