# Manage AI models in the registry

The AI Model Registry lists every AI model Rational AI can use. From it you register models from your providers, describe what each model can do, see where it is used, approve it, and pick the default models. To deploy and run models you host yourself, see [Deploy and run self-hosted models](/operational-guides/model-deployments).

:::note[What is the AI Model Registry?]
A [large language model](/reference/glossary#large-language-model-llm), or LLM, is the AI that actually generates text, embeddings, or images. Those models come from providers (OpenAI, OpenRouter, Xference, and others), and each provider is wired in through a *connector*. The registry lists the models those connectors expose, with what each one can do, what it costs and who approved it.
:::

## Prerequisites

Before you start, make sure you have:

- **Permissions**: the **AI Model Registry** row of your role, with **Create**, **Update** or **Delete** for the changes you make.
- **At least one connector**: a configured provider (for example OpenAI, OpenRouter, Xference, or an OpenAI Compatible endpoint) so the registry has models to list.

## Inspect a model

Go to **Settings** → **AI Model Registry** and select a model to open its details.

### Read a model's pricing

The **Pricing** section of a model's overview shows the costs set for it, such as **Cost per request** or **Cost per 1M input tokens**. Rows with no cost are hidden. To set prices, see [Cost metering](/cr/settings/ai-model-registry#cost-metering) and [Price what you are using](/operational-guides/govern-ai-applications#price-what-you-are-using).

### Read publisher and architecture

In the model picker, each entry shows a **publisher** chip and an **architecture** chip. The architecture is the model's design family, such as Llama or Mistral. Once the model is registered, its overview shows **Publisher** and **Architecture** fields.

### See where a model is used

Before you change or remove a model, check what uses it. The **Used in** section lists each consumer, the roles the model fills there, and a link to it:

- **Touchpoint**: as default, available, sentiment, topic or title model.
- **Knowledge base**: as the embedding model.
- **Conversations** (room configuration): as conversational, sentiment, topic or title model.
- **Fine-tuning**: as the base model.

## Describe what a model can do

What the registry says a model can do decides whether a chat may attach images, whether tools are sent, which reasoning levels the picker shows, and which sizes an image model is asked for. For a self-hosted model the registry often guesses from the name. Correct it when the guess is wrong.

### Edit capabilities and reasoning levels

1. Go to **Settings** → **AI Model Registry**, open the model's row menu and select **Edit details**.
2. In **Capabilities**, add or remove **Vision** (reads images), **Tool use** (can call tools) and **Reasoning** (thinks before it answers). This works for every model, third-party and self-hosted alike.
3. For a reasoning model, check **Reasoning levels**: *"The levels this model can be asked for, under the provider's own names."* They are guessed from the model's family; edit them to correct the guess.
4. Select **Save**.

### Set inference defaults and output caps

The same **Edit details** dialog has **Inference defaults**, applied to every request to the model: **Seed**, **Temperature**, **Top P**, **Presence Penalty** and **Maximum output tokens**: *"Cap to the number of tokens generated by the model, including both reasoning and output tokens."* A touchpoint's own generation limits override it for that touchpoint.

The model's overview also shows its **Context length** and **Max output tokens** as the provider reports them.

### Describe an image model

An image generation model carries an account of what it can be asked for: output sizes, pictures per request, reference images, seed, negative prompt, output formats, quality levels and more. The image tools offer only what the model declares.

1. Open an image generation model (**Image gen** in the **Purpose** column) and find the **Image capabilities** section. A chip says where the values came from: **From the provider** or **Set by hand**. A model nobody has described says so, and every setting stays on offer.
2. Select **Edit what this model accepts** to open the full form on its own page.
3. Switch on each setting the model has and fill in its values. For **Output size**, choose how the model is sized: **Shapes** (aspect ratios), **Fixed sizes** (written as `1024x1536`) or **Free dimensions**.
4. Select **Save**.

:::note[Values set by hand are no longer updated by the provider]
Once you save the form, the provider's catalog stops overwriting the model, so a correction you made stays made. To go back, select **Restore the provider's values**: what you entered is discarded and replaced by whatever the provider reports, which may be nothing at all.
:::

### Use decision models

A **Decision** model doesn't chat: it takes a structured question, with images if needed, and returns a decision. Decision models come from a System One Compatible or OpenRouter connector and show **Decision** in the **Purpose** column. Set one as the **Decision model** default (below) so that decisions that name no model, such as those run from [knowledge views](/operational-guides/knowledge-custom-views), have one to use.

## Document and approve a model

Each model's details have a **Governance** section where you record which exact model runs, under what license, for what use, and who approved it. It applies to third-party models too.

### The record

| Field | What it captures |
|-------|------------------|
| **Version** | The specific release in use |
| **Weights digest** | The fingerprint of the exact weights running |
| **Licence** | The terms the model is used under |
| **Provenance** | Where the model came from |
| **Intended purpose** | What the model may be used for, in prose |
| **Prohibited uses** | What it must not be used for |
| **Known limitations** | Where it is known to perform badly or unreliably |
| **Evaluation** | What testing was done and what it showed |

Don't confuse **Intended purpose** with **Purpose**, shown higher up the details: **Purpose** is the technical type (text generation, embedding, and so on), while **Intended purpose** describes the permitted use, such as "drafting replies to customer email".

### Approve a model

**Save** stores the record. **Approve** records the approval with who approved the model and when. **Approve** stays disabled until the model has an **Intended purpose**.

The approval state shows as a chip: **Approved**, **Not reviewed** or **Withdrawn**.

:::warning[Editing an approved record revokes its approval]
Saving a change to a substantive field of an approved model sets it back to **Not reviewed**. The section warns you before you save. Withdrawing an approval asks you to confirm first.
:::

## Set default platform models per task type

Pick the model the platform reaches for when a specific consumer hasn't pinned one of its own. These are fallbacks: a [touchpoint](/operational-guides/configure-touchpoints) or Knowledge with its own model always wins.

1. Go to **Settings** → **AI Model Registry**.
2. Open the **Default models** panel above the models table (*"Choose the model used by default for each task type."*).
3. Set any of these fields. All are optional and can be cleared. Each lists only enabled models of the matching purpose:
   - **Conversational model**: the default for conversations. Lists **Text gen** models. Used by chat when a touchpoint has no model of its own.
   - **Coding model**: the default for code generation. Lists **Text gen** models.
   - **Agents model**: *"Used by agents without a model override."* Lists **Text gen** models.
   - **Embedding model**: the default for embeddings. Lists **Embeddings** models. Used by knowledge creation when no embedding model is supplied.
   - **Image generation model**: the default for image generation. Lists **Image gen** models. Used by image requests that don't name a model of their own.
   - **Decision model**: the default for decisions. Lists **Decision** models. Used by decisions that name no model, such as those of knowledge views.
4. Select **Save**.

## Require approval before a model answers

When **Require approval** is on, a model answers chats, agents, API calls and knowledge processing only after it has been approved (see [Approve a model](#approve-a-model)).

1. Go to **Settings** → **AI Model Registry**.
2. In the **Model approval** section, read the current state. It names the models that have not been reviewed.
3. Turn on **Require approval**.
4. Read the confirmation. It lists the models that will refuse every request until someone approves them.
5. Select **Require approval** to confirm.

| Approval state | **Require approval** off (default) | **Require approval** on |
|---|---|---|
| **Approved** | Answers | Answers |
| **Not reviewed** | Answers | Refused |
| **Withdrawn** | Refused | Refused |

While approval is required, the models list shows an **Approval** column, and model pickers offer only models that can answer. Editing an approved model's record revokes its approval, so with **Require approval** on the model refuses requests until it is approved again.

Approvals, revoked approvals and changes to the policy are written to the [audit trail](/operational-guides/audit-trail).

## Add a provider connector

A connector is the bridge between the registry and an external model provider. Go to **Settings** → **Connectors**, select **Add**, and pick the connector that matches your provider. The two below cover the cases where the setup isn't obvious.

### Add Xference

Xference needs only an API key, with no endpoint to enter.

1. In the **Add a new connector** dialog, choose **Xference**.
2. Enter your **API key**.
3. Save. The available models are discovered from Xference.

### Add an OpenAI Compatible provider

Use this when your provider offers an OpenAI-compatible API but has no dedicated connector.

1. In the **Add a new connector** browser, choose **OpenAI Compatible**.
2. Fill in both required fields:
   - **Base URL**: the OpenAI-compatible endpoint of your provider.
   - **API Key**: the key for that endpoint.
3. Save.
