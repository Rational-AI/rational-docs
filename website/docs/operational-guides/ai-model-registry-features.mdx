# Manage AI models in the registry

The AI Model Registry is where every AI model the platform can use lives in one place. From here you connect providers, register their models, describe what each model can do, read what it costs and where it's already in use, and pick the defaults the rest of the platform falls back on. To deploy and run models you host yourself, see [Deploy and run self-hosted models](/operational-guides/model-deployments). This guide covers all of that, end to end.

:::note[What is the AI Model Registry?]
A [large language model](/concepts/LLMs), or LLM, is the AI that actually generates text, embeddings, or images. Those models come from providers (OpenAI, OpenRouter, Xference, and others), and each provider is wired in through a *connector*. The registry is the catalog that ties it together: add a connector, register the models it exposes, inspect each model's pricing, publisher, and usage, and choose the platform default model for each kind of task so the rest of the platform inherits a sensible fallback.
:::

## Prerequisites

Before you start, make sure you have:

- **Permissions**: the **AI Model Registry** row of your role, with **Create**, **Update** or **Delete** for the changes you make.
- **At least one connector**: a configured provider (for example OpenAI, OpenRouter, Xference, or an OpenAI Compatible endpoint) so the registry has models to list.

## Inspect a model

Open any model to see its full profile: what it costs, who published it, how it's built, and what's relying on it. Go to **Settings** → **AI Model Registry** and select a model to open its details. The sections below walk through each part of that view.

### Read a model's pricing

Check what a model costs before you make it a default or point a new workload at it.

The **Pricing** section appears on a model's overview only for models that have pricing configured (for example a self-hosted model with a cost set). Costs are shown in the units people think in, so you may see any of:

- **Cost per request**
- **Cost per hour**, **Cost per minute** or **Cost per second**, depending on the time unit set for the model
- **Cost per 1M input tokens**, **Cost per 1M output tokens**, **Cost per 1M cached input tokens**, **Cost per 1M cache-write tokens** and **Cost per 1M reasoning tokens**
- **Cost per image** and **Cost per web search**

:::note[Only priced rows are shown]
Pricing chips appear only when pricing is enabled for the model, and any row with no cost is hidden. A model priced only per token, for instance, won't show a per-request chip.
:::

### Read publisher and architecture

When a model is open source, knowing who published it and what architecture it's built on tells you what you're actually running.

Both facts show up in two places. In the model picker, each entry carries a **publisher** chip (with the provider's icon, falling back to the Hugging Face mark) next to an **architecture** chip. The architecture is the model's underlying design family, such as Llama or Mistral. Once the model is registered, its overview shows dedicated **Publisher** and **Architecture** fields.

### See where a model is used

Before you change or remove a model, see what's leaning on it, so you don't quietly break a conversation or a [Knowledge](/operational-guides/create-knowledge).

Scroll to the **Used in** section, below the overview. Each entry shows its kind, the roles the model fills there, and a link through to that consumer:

- **Touchpoint**: as default, available, sentiment, topic or title model. A touchpoint is a configured entry point where users talk to the AI, such as a chat widget or channel.
- **Knowledge base**: as the embedding model. An embedding is the numeric representation of text that powers search and retrieval.
- **Conversations** (room configuration): as conversational, sentiment, topic or title model.
- **Fine-tuning**: as the base model.

If nothing references the model, the section shows an empty state.

## Describe what a model can do

The platform decides what to offer around a model from what the registry says it can do: whether a chat may attach images, whether tools are sent, which reasoning levels the picker shows, which sizes an image model is asked for. Catalogs get this right most of the time; for a self-hosted model the registry can often only guess from the name. Correct it here when the guess is wrong.

### Edit capabilities and reasoning levels

1. Go to **Settings** → **AI Model Registry**, open the model's row menu and select **Edit details**.
2. In **Capabilities**, add or remove **Vision** (reads images), **Tool use** (can call tools) and **Reasoning** (thinks before it answers). This works for every model, third-party and self-hosted alike.
3. For a reasoning model, check **Reasoning levels**: *"The levels this model can be asked for, under the provider's own names."* They are guessed from the model's family; edit them to correct the guess.
4. Select **Save**.

### Set inference defaults and output caps

The same **Edit details** dialog has **Inference defaults**, applied to every request to the model: **Seed**, **Temperature**, **Top P**, **Presence Penalty** and **Maximum output tokens**: *"Cap to the number of tokens generated by the model, including both reasoning and output tokens."* Use the cap to stop a model from writing far longer answers than you pay for. A touchpoint's own generation limits override it for that touchpoint.

The model's overview also shows its **Context length** and **Max output tokens** as the provider reports them, which the platform uses to size what it sends.

### Describe an image model

An image generation model carries an account of what it can be asked for: output sizes, pictures per request, reference images, seed, negative prompt, output formats, quality levels and more. The image tools offer only what the model declares, so a request never asks for a size the model refuses.

1. Open an image generation model (**Image gen** in the **Purpose** column) and find the **Image capabilities** section. A chip says where the values came from: **From the provider** or **Set by hand**. A model nobody has described says so, and every setting stays on offer.
2. Select **Edit what this model accepts** to open the full form on its own page.
3. Switch on each setting the model has and fill in its values. For **Output size**, choose how the model is sized: **Shapes** (aspect ratios), **Fixed sizes** (written as `1024x1536`) or **Free dimensions**.
4. Select **Save**.

:::note[Values set by hand are no longer updated by the provider]
Once you save the form, the provider's catalog stops overwriting the model, so a correction you made stays made. To go back, select **Restore the provider's values**: what you entered is discarded and replaced by whatever the provider reports, which may be nothing at all.
:::

### Use decision models

A **Decision** model doesn't chat: it takes a structured question, with images if needed, and returns a decision. Decision models come from a System One Compatible or OpenRouter connector and show **Decision** in the **Purpose** column. Set one as the **Decision model** default (below) so that decisions that name no model, such as those run from [knowledge views](/operational-guides/knowledge-custom-views), have one to use.

## Document and approve a model

The registry answers *which model, served by whom, on what hardware, at what price*. A risk function or a public tender asks a different set of questions: which exact weights are running, under what license, approved for what use and forbidden for what, with which known limitations, and who signed that off.

The **Governance** section of a model's drawer is where those answers live. It applies to third-party models too, which are usually the ones drawing the hardest questions.

### The record

| Field | What it captures |
|-------|------------------|
| **Version** | The specific release in use |
| **Weights digest** | The fingerprint of the exact weights running |
| **Licence** | The terms the model is used under |
| **Provenance** | Where the model came from |
| **Intended purpose** | What the model may be used for, in prose |
| **Prohibited uses** | What it must not be used for |
| **Known limitations** | Where it is known to perform badly or unreliably |
| **Evaluation** | What testing was done and what it showed |

:::warning[Intended purpose is not the model's purpose]
Two near-identical names answering completely different questions:

- **Purpose**, shown higher up the drawer, is the technical **modality**: text generation, embedding, and so on.
- **Intended purpose**, in this section, is prose about **permitted use**, such as "drafting replies to customer email".

Removing exactly this ambiguity is what the governance record is for, so it's worth being deliberate about which one you're reading.
:::

### Documenting and approving are separate acts

**Save** writes documentation. **Approve** records a decision and stamps who took it and when. They're separate controls because they're separate acts, usually taken by different people. Folding them together would make *"I changed the intended purpose"* indistinguishable from *"I approve the new intended purpose"*.

The approval state shows as a chip. It reads as satisfied only when the model is approved; **Not reviewed** and **Withdrawn** both read as a caution rather than a failure, since neither is an error. They're not a sign-off.

:::warning[Saving an approved record revokes its approval]
Edit a substantive field on an approved model and the approval decays to **Not reviewed**, clearing the sign-off stamp. The section warns you before you save and again afterwards.

This is the behavior you want. An approval that outlives a rewrite of the thing approved is worse than no approval, because it reads as a decision somebody actually took. The case it guards against is repurposing: an approved model quietly edited from "drafting replies to customer email" to "screening job applicants", still wearing its sign-off.

Withdrawing an approval asks you to confirm first, and editing afterwards does not restore it.
:::

**Approve** stays disabled until the model has an **intended purpose**. Approving a model for an unstated use isn't a decision anyone can act on later.

## Set default platform models per task type

Pick the model the platform reaches for when a specific consumer hasn't pinned one of its own. These defaults are pure fallbacks: a [touchpoint](/operational-guides/configure-touchpoints) or Knowledge with its own model always wins.

1. Go to **Settings** → **AI Model Registry**.
2. Open the **Default models** panel above the models table (*"Choose the model used by default for each task type."*).
3. Set any of these fields. All are optional and can be cleared. Each lists only enabled models of the matching purpose:
   - **Conversational model**: the default for conversations. Lists **Text gen** models. Used by chat when a touchpoint has no model of its own.
   - **Coding model**: the default for code generation. Lists **Text gen** models. Stored for future use.
   - **Agents model**: *"Used by agents without a model override."* Lists **Text gen** models.
   - **Embedding model**: the default for embeddings. Lists **Embeddings** models. Used by knowledge creation when no embedding model is supplied.
   - **Image generation model**: the default for image generation. Lists **Image gen** models. Used by image requests that don't name a model of their own.
   - **Decision model**: the default for decisions. Lists **Decision** models. Used by decisions that name no model, such as those of knowledge views.
4. Select **Save**. Your selection is saved to the active platform configuration.

:::note[The coding default is the only one nothing reads yet]
The **Conversational**, **Agents**, **Embedding**, **Image generation** and **Decision** defaults are all used today. The **Coding** default is stored and shown so that code generation inherits it when it ships.
:::

## Require approval before a model answers

The registry can refuse every model that nobody has approved yet. The **Model approval** panel, below **Default models**, has a **Require approval** switch: when it is on, a model answers chats, agents, API calls and knowledge processing only after it has been approved in its **Governance** section (see [Document and approve a model](#document-and-approve-a-model)). Before you turn it on, the panel lists the models that would start refusing requests. A model whose approval was withdrawn is refused either way.

For how approval fits with the rest of your AI governance, see [Govern AI applications](/operational-guides/govern-ai-applications).

## Add a provider connector

A connector is the bridge between the registry and an external model provider. Go to **Settings** → **Connectors**, select **Add**, and pick the connector that matches your provider. The two below cover the cases where the setup isn't obvious.

### Add Xference

Reach for Xference when you want a model provider running with nothing but an API key, with no endpoint URL to look up or paste.

Xference is a one-click connector that uses a fixed OpenAI-compatible endpoint behind the scenes.

1. In the **Add a new connector** dialog, choose **Xference**.
2. Enter your **API key**.
3. Save. The platform discovers the available models from the Xference endpoint and proxies chat through the same path as OpenRouter.

:::note[Trial endpoint only]
Xference currently resolves only its trial host (`api-trial.xference.ai`). There is no production host yet, so this connector targets the trial endpoint until one is available.
:::

### Add an OpenAI Compatible provider

Use this when your provider speaks the OpenAI API but isn't one of the dedicated connectors. Here you supply the endpoint yourself.

1. In the **Add a new connector** browser, choose **OpenAI Compatible**.
2. Fill in both required fields:
   - **Base URL**: the OpenAI-compatible endpoint of your provider.
   - **API Key**: the key for that endpoint.
3. Save. The connector behaves exactly like the OpenAI connector but talks to your custom base URL.
