# Schedule and trigger agents

Some work should happen without anyone asking: the morning briefing at eight, the sales report every Monday, a review every time a pull request is opened. A **routine** is an agent that is started by something other than you: a schedule, a call from another system, a GitHub event, a new email, a new Knowledge file or a changed record. This guide shows how to set each one up, how to see what is coming and how to hold a routine.

:::note[A routine is an agent with a trigger]
There is nothing to create besides the agent: its **Trigger** decides what starts it. A scheduled or event-driven run is the same as any other run (same instructions, same tools, same approvals), and it shows up in **History**, on the agent's page and on the routine's **Runs** tab.
:::

## Prerequisites

- **An agent with instructions**: see [Build an agent](./create-an-agent). Write them for a run nobody is watching, and say where the result goes and what "done" means.
- **For GitHub:** admin rights on the repository, to add a webhook.
- **For API calls:** an API key from **Settings** → **API Keys** (see [Access Rational AI via API](/operational-guides/api-access#create-an-api-key)).
- **For new emails:** an Email channel (see [Connect a mailbox](/operational-guides/connect-email)).
- **For new files and changed records:** a Knowledge base the agent may use.

Search with **Search routines…**, filter by trigger (**Trigger: Scheduled**, **Trigger: Event**, **Trigger: API**) and by status (**Status: Enabled**, **Status: Paused**, **Status: Last run failed**), and sort by **Recently run**, **Name**, **Status** or **Failing first**; **List view** and **Grid view** switch the layout.

## Run it on a schedule

**Scout** writes the market briefing every weekday at 08:00, Rome time.

1. Open the agent's profile (**Edit**), or create it with **New routine**.
2. Under **Trigger & execution**, set **Trigger** to **Schedule**.
3. Under **Schedule**, keep **Cron** and enter the expression: `0 8 * * 1-5`.
4. Set the **Time zone**, for example `Europe/Rome`. Without one, the schedule follows the server's time zone.
5. Select **Save** (or **Create agent** for a new one).

<img
  alt="Scout's Trigger and execution section: trigger schedule, Cron 0 8 * * 1-5, timezone Europe/Rome, cloud, autonomous"
  src={require('@site/static/img/screens/agents-trigger-schedule.png').default}
  style={{ maxWidth: '520px', width: '100%', borderRadius: 8, border: '1px solid #e5e7eb' }}
/>

The cron expression has the usual five fields (minute, hour, day of the month, month, day of the week):

| Expression | Runs |
|------------|------|
| `0 8 * * 1-5` | At 08:00, Monday to Friday |
| `0 7 * * 1` | At 07:00 every Monday |
| `*/30 8-18 * * 1-5` | Every 30 minutes from 08:00 to 18:30, on weekdays |
| `0 6 1 * *` | At 06:00 on the first day of every month |

If a scheduled run is due while the previous one is still going, it is not stacked on top of it. When the agent has no model of its own, the platform Agents default is picked when the run starts.

:::note[Use cron, not interval]
The **Interval** option (**Every** *n* **minutes**) does not create a schedule yet, and saving a profile with it removes the cron schedule the agent had. For a regular interval, write it as a cron expression, such as `*/15 * * * *` for every 15 minutes.
:::

## Run it on a GitHub event

**Rev** reviews every pull request opened on `acme/web-shop`. GitHub calls Rational AI with a signed webhook, and each delivery starts a run whose input is the event payload.

### Configure the agent

1. In the profile, set **Trigger** to **GitHub event**.
2. **Repository**: `organisation/repository`, for example `acme/web-shop`. Deliveries from any other repository are ignored.
3. **Events**: a comma-separated list of GitHub event names, for example `pull_request` or `pull_request, push`. Write `event.action` to match a single action, for example `pull_request.opened`. Leave it empty to accept every event.
4. Optionally, narrow it further with **Only if** and **AI check** (see [Filter events before they start a run](#filter-events-before-they-start-a-run)).
5. Select **Save**.

<img
  alt="Rev's Trigger and execution section: trigger githubEvent, repository acme/web-shop, events pull_request"
  src={require('@site/static/img/screens/agents-trigger-github.png').default}
  style={{ maxWidth: '520px', width: '100%', borderRadius: 8, border: '1px solid #e5e7eb' }}
/>

### Generate the webhook secret

The secret is what proves a delivery came from your repository. It is generated through the API, with an API key and the agent's ID (the last part of the agent's page address, `/agents/team/<agent id>`):

```bash
curl -X POST "https://<your address>/api/agents/v0/agents/<agent id>/webhook-secret" \
  -H "Authorization: Bearer $RATIONAL_AI_API_KEY"
```

The answer is `{"secret":"…"}`. It is shown only this once: store it for the next step. Calling the endpoint again replaces the secret, and GitHub deliveries signed with the old one are refused.

### Add the webhook on GitHub

In the repository, go to **Settings** → **Webhooks** → **Add webhook** and fill in:

| Field | Value |
|-------|-------|
| **Payload URL** | `https://<your address>/api/agents/v0/webhooks/<tenant>/<agent id>/github` |
| **Content type** | `application/json` |
| **Secret** | the secret from the previous step |
| **Which events** | the events you listed on the agent |

`<tenant>` is your organization's identifier on the platform, normally the first part of your Control Room address (`<tenant>.…`); your administrator can confirm it.

GitHub sends a *ping* as soon as the webhook is saved; the answer `{"status":"pong"}` in **Recent Deliveries** confirms that the address and the secret are right. From then on, every matching event answers `{"status":"queued","runId":"…"}` and a run appears in **History** started by *GitHub event*.

| GitHub shows | Means |
|--------------|-------|
| `401` | Wrong agent ID, the agent's trigger is not **GitHub event**, or the signature does not match the secret. Regenerate the secret and paste it again. |
| `{"status":"ignored","reason":"paused"}` | The agent is paused or disabled. |
| `{"status":"ignored","reason":"limit"}` | The agent has used its monthly budget. |
| `{"status":"ignored","eventName":"…"}` | The event is not in the agent's **Events** list, or it comes from another repository. |
| `{"status":"skipped","runId":"…"}` | The event did not pass **Only if** or **AI check**. |
| `{"status":"duplicate"}` | GitHub redelivered an event that already started a run. |

## Start it from a webhook

Any system that can send an HTTP POST (a form tool, a monitoring alert, a CRM automation) can start a run, without an API key.

1. In the profile, set **Trigger** to **Webhook** and save the agent. Its **Address** appears.
2. Select **Generate key** and copy the key: it is not shown again. **Rotate key** replaces it, and systems still sending the old key are refused.
3. Send each request to the **Address**, with the key as a bearer token (`Authorization: Bearer <key>`), or sign the raw body with it (HMAC-SHA256) in an `X-Signature-256` header.

Each request starts a run whose input is the request body (up to 256 KB). An `Idempotency-Key` header makes a repeated request start no second run. Requests to a paused or over-budget agent are acknowledged without starting a run, and **AI check** can skip the ones that do not concern the agent.

## Start it on a new email

1. In the profile, set **Trigger** to **New email**.
2. Under **Mailbox**, choose an Email channel.
3. Optionally, set **Only if** on **From**, **Subject**, **Text**, **Has attachments** or **Attachment names**, and an **AI check**.
4. Select **Save**.

Each mail the channel receives starts a run with the sender, subject, text and attachments.

## Start it on a new file or a changed record

For **New file**, choose the **Knowledge** and, optionally, a **Collection** (**Every file** by default). Each file of the base, or of the collection, that finishes processing starts a run with the file and its records.

For **Record changed**, choose the **Knowledge**, optionally a **Collection** (**Every record**), **When** (**Created or updated**, **Created** or **Updated**), the **Fields** whose change counts, and an **Only if** filter. Each record created or changed starts a run within a minute, one run per record however many saves it took. The agent's own changes never start it; other agents' changes do, so two agents that write each other's records can start each other in turn.

When the agent's **Knowledge access** lists specific bases, the trigger's Knowledge must be one of them.

## Filter events before they start a run

For **GitHub event** and **New email**, **Only if** keeps only the events that match a filter. For those two and **Webhook**, **AI check** asks a yes-or-no question about each event, such as *"Is this a purchase order?"*, and starts a run only when the answer is yes with at least the confidence you set (*% sure*).

An event that does not pass starts no run and shows as *Skipped* in **History**. The AI check uses the cheapest model of the agent's own provider and counts toward the agent's budget; when the check itself fails, the event starts its run.

## Start it from another system

Any system that can make an HTTP request (a CRM, a ticketing tool, a nightly script) can hand work to an agent:

```bash
curl -X POST "https://<your address>/api/agents/v0/agents/<agent id>/execute" \
  -H "Authorization: Bearer $RATIONAL_AI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "task": "Prepare the offer for RFQ-2026-0161 (Kessler Agritech)",
        "instructions": "Three lines of M12 hex bolts, zinc flake. Price them and write the offer file.",
        "input": { "rfq": "RFQ-2026-0161", "customer": "Kessler Agritech" }
      }'
```

- `task`: the one-line goal of the run, shown in History.
- `instructions`: optional details for this run; the profile's instructions still apply.
- `input`: optional JSON the agent receives as-is.

The answer is the new run, with its `id` and `status`; follow it at `/agents/runs/<run id>`. The key acts as an administrator; add an `X-USER-ID: <user id>` header to act as a specific user, with that user's permissions. Setting the agent's trigger to **API** marks it as API-driven in **Routines**; an agent with any trigger can be started this way.

## Pause an agent

**Pause** (on the agent's page or its row in **Routines**) marks the agent as *Paused*: its schedule stops firing, its other triggers no longer start runs, and its upcoming runs leave the calendar. **Resume** clears it.

An agent can also be paused for you:

- *Budget reached*: the agent used its **Monthly budget**. Raise or remove the budget on the agent's page to resume it.
- *Paused: unread*: with **Pause scheduled agents nobody reads** turned on in **Settings** → **Agents**, a scheduled agent is paused when nobody opened its last 10 results over at least 14 days. Its owner is notified and can resume it.
