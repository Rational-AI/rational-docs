# Run models on your own servers

When Rational AI is installed on your premises, the reason is usually that data must not leave them, and that includes the prompts and documents you send to a model. An on-premises installation therefore runs its models itself, on the same machine as the platform or on extra machines you add for them. You choose and deploy every model from **Settings** → **AI Model Registry**, as in the cloud; this guide covers what is specific to your own servers: GPUs, memory, the weights on disk, the DGX Spark, and spreading models over several machines.

:::note[What runs a model on-premises?]
Each deployed model is a container on the Docker engine of your server, next to the platform's own services. Text generation models run on **vLLM**, an open-source inference engine; embedding models run on vLLM or on **text embeddings inference** (TEI). The platform starts, stops and watches these containers for you: you never run Docker commands to deploy a model. With several machines, the containers are spread over a **Docker Swarm**, a group of Docker engines that work as one.
:::

## Prerequisites

Before you start, make sure you have:

- **An on-premises installation** of the current release, with administrative access to the Control Room.
- **Hardware for the models:** an NVIDIA GPU with its container runtime for good speed, or enough memory to run small models on the CPU.
- **A Hugging Face token, for gated models only:** models such as Llama or Gemma need your organization's own token, which Rational AI sets on the installation. Public models (for example `BAAI/bge-m3`) need none.

## Add your first models

A new installation starts with **no models**: no embedding model and no chat model. Until you add them, a Knowledge cannot index documents and chats cannot answer.

1. Go to **Settings** → **AI Model Registry** and select **Add new** → **Choose an open source model**.
2. Add an **embedding model** first, for example `BAAI/bge-m3`, and deploy it.
3. Add a **text generation model** that fits your hardware, and deploy it.
4. In the **Default models** panel of the same page, set the **Embedding model** and the **Conversational model** to the models you added.

Each deployment downloads its weights first, then starts; the **Deployment** section of the model follows it to **Ready**. For the details of deploying, scaling and stopping models, see [Deploy and run self-hosted models](/operational-guides/model-deployments).

:::note[Chat models need their tool-call parser]
Every Knowledge and touchpoint chat gives the model tools, and vLLM refuses tool calls from a model started without a tool-call parser. Rational AI fills in the parser of the model's family by default (and, for a thinking model, its reasoning parser). If every answer of a new chat model fails, check those two fields in its **Deploy settings**.
:::

## Understand GPU and CPU

The platform detects what the host offers:

- **With the NVIDIA runtime** in Docker, a text generation model gets one GPU unless its deploy settings say otherwise.
- **Without it**, vLLM runs on the CPU. It works, but much more slowly: keep CPU deployments to embedding models and small chat models.

You can always change the number of GPUs in a model's deploy settings; `0` runs it on the CPU.

Each deployment reserves a share of its GPU's memory, set by its **GPU memory budget**: a share (`85%`), a size (`24GiB`) or both (`100% - 1.5GiB`). When several models share a GPU, give each its own budget so that they fit together.

## Know where the weights are kept

Model weights are large, so the platform keeps them out of the way:

- **One cache for all models.** The weights download into a Docker volume, `rai-model-cache`, shared by every model container. A model is downloaded once and survives restarts and redeployments.
- **Out of the backup.** The [backup](/operational-guides/backup-and-restore) leaves the weights out, since they can always be downloaded again. The local backup taken before every update also leaves out the captured model calls, so a rollback brings them back empty.
- **Kept when a model is removed.** Deleting a deployment leaves its weights in the cache. Rational AI can reclaim that disk once no model runs.

:::note[Model containers are kept away from your data]
Model containers sit on a network of their own, shared only with the platform's backend. A model can answer requests, but cannot reach the databases or any other part of the platform.
:::

## Run models on a DGX Spark

An NVIDIA DGX Spark is an Arm machine whose GPU (a GB10) shares its memory with the rest of the system. The installation recognizes it and adjusts:

- **The right images.** It uses the Arm builds of the embedding runner, built for the GB10.
- **80 GiB for models.** Because the platform needs memory too, the installation leaves 80 GiB of the shared memory to models and keeps the rest. A deployment's GPU memory budget counts against those 80 GiB, so `50%` means 40 GiB.
- **Tuned defaults.** Models deploy with the settings their vLLM recipes give the DGX Spark. Where no recipe covers a model, a configuration measured on a DGX Spark applies: `BAAI/bge-m3` on one GPU, and `RedHatAI/Qwen3.6-35B-A3B-NVFP4` with a 32,768-token context, 16 concurrent requests and a `60GiB` budget.

:::warning[Budgets are not reserved in advance]
If several models' budgets add up to more than 80 GiB, they don't all start: vLLM refuses to start without the free memory it was given. Size the budgets so that the models you want running at the same time fit together.
:::

## Spread models over several machines

One machine may not have enough GPUs for every model you need. Rational AI can add **model nodes**: machines that only run models, joined to the machine with the platform in a Docker Swarm. You keep deploying from **Settings** → **AI Model Registry**, and each deployment runs wherever there is room for it, with as many replicas as you ask for.

- **Every node must be the same kind of machine.** All nodes need the same processor architecture, and ideally the same hardware: a DGX Spark and an x86 server can't share a swarm.
- **GPUs are counted.** Every node declares its GPUs to the swarm, and a deployment reserves as many as it has, so two models never share a card by accident. A node without GPUs runs models on the CPU.
- **Each node keeps its own weights.** A node downloads the weights of the models it runs into its own cache. On DGX Sparks, the 80 GiB for models apply to each node.
- **Models are deployed again once.** When the machine with the platform starts managing a swarm, the models that ran on it are removed: deploy them again from **Settings** → **AI Model Registry**.

Your firewall must let the machines reach each other on these ports. The installation opens nothing itself.

| Port | Between |
|---|---|
| 2377/tcp | every node → the machine with the platform |
| 7946/tcp and 7946/udp | all nodes |
| 4789/udp | all nodes |
| IP protocol 50 (ESP) | all nodes (the encryption of the models network) |

## Move from an earlier release

Installations from earlier releases ran their models outside the registry, on an engine of their own (`text-llm`, or a vLLM behind a gateway, with optional inference nodes). Moving to a current release removes that engine. After the move, as an administrator:

1. **Expect the old models to fail.** Their deployments show **Failed** because their engine no longer exists.
2. **Add them again as registry models** and deploy them: the embedding model first (`BAAI/bge-m3` embeds like the old `bge-m3:latest`), then the chat model.
3. **Move the defaults and the touchpoints** to the new models, then delete the old models and their *Inference* connector.
4. **Check each Knowledge.** A Knowledge keeps the embedding model it was indexed with; point it at `BAAI/bge-m3` to keep its existing vectors. Another embedding model means indexing again.
Rational AI frees the disk the old engine used once the new models run.
