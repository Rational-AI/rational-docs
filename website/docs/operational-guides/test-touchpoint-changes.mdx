# Test a touchpoint change before it goes live

Replay testing re-runs a touchpoint's past conversations against a pending change to its prompt or models, and shows what came out different before your users see it. The baseline is what the assistant did on real conversations, so a run tells you whether behavior changed, not whether an answer is good.

## Prerequisites

- **Permission to update the touchpoint.** Without it the touchpoint's form is read-only.
- **A touchpoint with history.** Testing is offered once a touchpoint has at least five past conversations it can replay.
- **A change to the system prompt, the default model, or the model pool.** Other edits, such as the description, save without the offer.

## Run a test

1. Make your change to the touchpoint and select **Save**. A dialog asks *"Test the change first?"*. The **Default touchpoint** never asks: its changes save straight away.
2. Choose which conversations to replay:
   - **Most recent conversations, up to** a number you set: 20 by default.
   - **Only conversations with negative feedback**: the ones users already rated badly.
   - **Choose conversations manually**: pick from the touchpoint's 100 most recent conversations.
3. Check the **Estimated cost**, which updates with your selection. A run replays at most 100 conversations.
4. Select **Test first**. To skip the test, select **Save without testing**; to save nothing, select **Cancel**.

If the cost estimate can't be loaded, the dialog doesn't appear and your change saves normally.

## What happens during a run

Your change is applied to a temporary copy of the touchpoint. The live touchpoint stays as it was until you select **Apply change**.

Tools are never called during a replay. When the assistant calls a tool, it gets the result that tool returned in the original conversation, so no email is sent twice and no record is written again. If the changed assistant tries a tool call the original conversation never made, there is no result to give it: the case is marked **Diverged** and stops, and you can see which call it wanted to make.

Replayed conversations don't appear in your conversation lists or statistics, get no titles, topics or sentiment, and are never sent to a channel. Their model cost shows in [Governance](/operational-guides/governance) as its own line, so it doesn't add to the live touchpoint's spend.

## Read the results

Each conversation gets one verdict:

| Verdict | Meaning |
|---------|---------|
| **Unchanged** | No meaningful difference. |
| **Changed** | Behavior differed on at least one signal. |
| **Diverged** | The assistant tried a tool call the original never made, so the case stopped. |
| **Failed** | The case couldn't be completed. |

Diverged and changed cases are listed first. Expand a row to see the original conversation (**Now**) and the replayed one (**After the change**) side by side. To stop a run in progress, select **Cancel run**.

A case counts as changed when the assistant called different tools, cited different sources, returned an error or an empty answer, or changed the form of its answer (for example, no longer valid JSON, or much shorter or longer). Different wording alone doesn't count. Cost and response time are shown and flagged when they more than double, but they don't affect the verdict.

In a conversation with several turns, compare only up to the first difference. After it, the replay is answering a different conversation from the original.

## Apply or discard

When the run finishes, the footer sums up the verdicts and the cost.

- **Apply change** saves your edits to the touchpoint.
- **Discard** throws the change away.

Past runs stay available, read-only, on the touchpoint's **Test runs** tab, with their date, status, summary, and cost.

## Limits

- Anonymous conversations are left out of the most recent and negative-feedback selections.
- Attachments aren't replayed, so a case that depended on a document isn't a faithful reproduction.
