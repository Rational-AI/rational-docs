# Retrieval-Augmented Generation (RAG)

**Retrieval-Augmented Generation (RAG)** is a technique that enhances Large Language Models (LLMs) by retrieving relevant information from a **knowledge base** before generating a response.

Instead of relying only on what the model learned during training, a RAG system actively searches your organization’s knowledge, selects the most relevant resources, and provides them as context.\
The response is therefore **grounded in your data**, not only in general knowledge.

This approach improves: accuracy, relevance, domain alignment, transparency of sources, and user trust.

Rational Knowledge provides two RAG strategies: **Naive RAG** for fast semantic search; and **Graph RAG** for relationship-aware retrieval.

## Naive RAG

Naive RAG is the simplest and fastest retrieval approach. It performs **semantic search** using vector embedding and retrieves the most relevant documents **based purely on meaning**.



**Pipeline**: User query → Embedding → Vector search → Top-K results → Context window filter → LLM

The process works as follows:

1. The user query is converted into an **embedding** (a numerical representation of its meaning).

2. That embedding is compared against document embeddings stored in the knowledge base.

3. **Similarity** **is calculated** using cosine similarity.

4. Results above a **semantic threshold are ranked**.

5. The top results that fit within the model's **context window** are passed to the LLM.



Naive RAG performs a **single search operation**, treats each document independently, and produces no relationship traversal. It is fast and well-suited for direct, well-defined questions.

It works best when:

- The knowledge base has no explicit document relationships
- The query is specific and the answer is likely contained in one document
- Fast response time is a priority



For example, if the query is:

```
What are the symptoms of diabetes?
```

Naive RAG retrieves documents about diabetes symptoms based on semantic similarity, without pulling in related resources like treatment guidelines or clinical studies.



## Graph RAG

**Graph RAG** extends semantic search by incorporating **knowledge graph relationships**. It retrieves not only directly relevant documents, but also related resources connected through **explicit relationships**.

\
**Pipeline**: User Query → Embedding → Vector Search → Top-K Results → Graph Expansion → Relevance Filtering → Final Ranking → Context Window Filter → LLM

The process occurs in three  phases:

1. **Semantic search**: identical to Naive RAG. The query is embedded, semantically similar documents are retrieved, and results are filtered by a semantic threshold.

2. **Graph expansion**:

   - For documents that score above the graph expansion threshold, the system considers their relationships to find related resources.
   - **Combined scores** are calculated using both **semantic similarity** and **keyword overlap**, then filtered by a relevance threshold.

3. **Final ranking**: all results from both phases are merged, sorted by combined score, and fitted into the context window before being passed to the LLM.



Graph RAG is slower than Naive RAG but produces a **richer result set**. It is better suited for broad or multi-dimensional queries where connected context adds value

It works best when:

- **Relationships** between documents matter (citations, references, hierarchies);
- The query is vague, broad, or multi-layered;
- The knowledge base is structured as a **graph**.



For example, if the query is:

```
What are the side effects of metformin?
```

Graph RAG first **retrieves** documents about metformin, then **expands** to related clinical trials, drug interactions, related medications, and patient case studies, **combining** all of them into the final context window.

## Naive RAG vs Graph RAG

| Aspect                 | Naive RAG          | Graph RAG                  |
| :--------------------- | :----------------- | :------------------------- |
| Retrieval Type         | Single-phase       | Multi-phase                |
| Relationship Awareness | No                 | Yes                        |
| Scoring                | Semantic only      | Semantic + keyword         |
| Speed                  | Faster             | Slower                     |
| Best For               | Flat document sets | Graph-structured knowledge |
| Output                 | Direct matches     | Direct + related resources |

## RAG and SQL tools

Rational AI agents can also access structured databases via **SQL tools** (SQLite and Postgres), allowing direct queries over relational data. Configuring a Touchpoint correctly means deciding not just which RAG strategy to use, but also when **SQL is more appropriate** than semantic retrieval.

### Tool Enablement

Tool availability should reflect the actual structure of the Knowledge environment:

- If no database is available, do not enable **SQL tools**
- If no documents have been ingested, do not enable **RAG tools**
- If documents have no relationships, **Naive RAG** is sufficient
- If documents have relationships, **Graph RAG** can be enabled, optionally alongside Naive RAG

### Retrieval Strategy

As a general rule, **RAG** **should be the default**. Most queries are in natural language and lack precise identifiers, making semantic search search the most reliable starting point.

When both RAG tools are available:

- Use **naive RAG** for simple, well-defined questions where the answer is likely in a single document;
- Use **graph RAG** for broader or more complex queries where document relationships add value.

### When to Use SQL

SQL is not suitable for general semantic search. Use it for structured operations:

- Exact matches using **unique identifiers** (IDs, exact names). When no unique identifier is available, maximize coverage using LIKE or ILIKE operators with relevant synonyms;
- **Aggregations** (COUNT, SUM, or AVG);
- **Numerical filters** (e.g., price thresholds, date ranges);
- Deterministic database queries.

### Combini RAG and SQL

For complex queries, use both together. A typical pattern:

1. Use **RAG** to identify relevant entities or retrieve contextual information;
2. Extract **structured** **data** such as IDs or categories;
3. Use **SQL** for precise filtering or aggregation.

RAG provides **semantic alignment**; SQL provides **structured precision**. Together, they enable accurate and context-aware retrieval across both unstructured and structured knowledge.
